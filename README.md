# DeepStudent-Go

A UI-first proof of concept for the DeepStudent desktop migration. This branch
explores a small React learning shell packaged with [MyGo](https://github.com/egoist/mygo)
and keeps the future Go runtime boundary explicit without claiming that the
runtime migration is complete.

> **Status: experimental / migration workspace**
>
> The UI is a working shell with local demo behavior. Chat responses come from
> an in-process `StubAdapter`; they are not generated by a model and are not
> sent to the Go runtime. The Go code in this branch only exposes a typed
> `HealthService` bridge for the desktop shell. Do not use this branch as a
> production client or as evidence that the backend migration is complete.

## What this branch contains

- Responsive React 19 + TypeScript + Vite learning shell
- First-run onboarding for learning goal, mode, model label, and runtime label
- Chat, learning resources, tasks, skills, flashcards, settings, and theme views
- MyGo desktop entry point and typed health bridge
- Versioned runtime envelope notes in [`protocol/runtime-v1.md`](protocol/runtime-v1.md)
- GitHub Pages and unsigned macOS arm64 workflow definitions

The browser and desktop shell share the same frontend bundle. Onboarding and
appearance preferences are stored in browser-local storage. The visible model
and runtime choices are currently preferences only; they do not select a live
provider.

## Architecture

```text
React shell (Vite)
  ├─ local StubAdapter for demo chat responses
  ├─ localStorage for theme/onboarding preferences
  └─ typed MyGo health bridge when running in the desktop shell
          │
          ▼
      Go `HealthService` (health only in this branch)

Future seam: versioned runtime.v1 request/event contract
```

`protocol/runtime-v1.md` describes the compatibility seam for a later runtime
implementation. It is a design contract, not an implemented API in this
branch. The backend implementation lives on `feature/go-backend-runtime` and
adds HTTP/SSE, persistence, and provider-neutral runtime packages.

## Technology

- Go 1.27.1 module and MyGo 0.1.22 desktop runtime
- React 19, TypeScript, Vite, and `@assistant-ui/react`
- Bun for workspace install and scripts (Node/npm lockfile is retained for

## Prerequisites

- Go 1.27.1 or a compatible newer Go toolchain
- Bun (the CI workflow uses Bun 1.2.21 for the Pages build)
- macOS 12+ arm64 and Xcode command-line tooling for a native macOS build
- GitHub Pages permissions if running the deployment workflow

Docker is intentionally not part of this shell-only branch. The Go service and
Compose profile are introduced on `feature/go-backend-runtime`; use that branch
when you need a local HTTP/SSE server or a container image.

## Develop locally

Install dependencies from the repository root, then start the Vite shell:

```sh
bun install
bun run dev:web
```

Open the URL printed by Vite (normally `http://localhost:5173`). The first
visit shows onboarding. Reset the demo state from the browser devtools by
clearing local storage keys `dstu-onboarding-config-v1` and
`dstu-theme-mode`.

The shell can also be run through MyGo after generating the typed bindings:

```sh
bun install
go install github.com/egoist/mygo/cmd/mygo@v0.1.22
mygo generate
bun run build -- -platform darwin/arm64
```

`mygo.config.ts` sets the development URL to Vite, embeds `frontend/dist` for
packaged builds, and configures macOS 12+ plus a Linux metadata profile. Builds
are unsigned (`signingIdentity: "-"`) and are intended for local evaluation.

## Build and test

Frontend checks that are available in this branch:

```sh
bun install
cd frontend
bun run typecheck
bun run build
```

The root scripts are equivalent shortcuts:

```sh
bun run build:web
```

There is no Go backend test suite or Go verification workflow on this branch.
The Go module is only the MyGo shell bridge, and this environment does not
provide a verified Go test run. Do not report `go test`, `go vet`, or a Go CI
check as passing for `migration/mygo-shell-poc`; the backend branch owns those
checks.

## Configuration

Build-time configuration is intentionally small:

- `VITE_DEPLOY_TARGET=pages` sets the `/DeepStudent-Go/` asset base path for
  GitHub Pages. Omit it for Vite development and MyGo (`/` base path).
- `mygo.config.ts` controls app identifier, version, dev command, bundle path,
  entry point, and platform metadata.
- The shell has no provider API URL, API key, or account configuration. The
  onboarding model/runtime fields are labels saved locally until a runtime
  adapter is implemented.

Never place provider credentials in `frontend`, `localStorage`, checked-in
configuration, or a Pages artifact. A future runtime should receive secrets
through its deployment environment or OS credential store.

## Security and privacy notes

- The current chat adapter is deterministic local demo code; it does not call a
  network provider.
- Onboarding and theme preferences are non-secret browser-local values. They
  are not encrypted or synchronized.
- The MyGo bridge currently reports health metadata only. It is not an auth
  boundary and should not be exposed as a remote service.
- The Pages workflow publishes the static frontend. Treat Pages as public and
  never include private notes, credentials, or user data in the bundle.
- Before connecting a real runtime, add origin checks, authentication, request
  limits, structured error handling, and a documented data-retention policy.

## GitHub Pages preview

The Pages workflow (`.github/workflows/pages-preview.yml`) builds
`frontend/dist` with the repository base path and deploys it through GitHub
Pages when the workflow is enabled for the repository. A successful workflow
run is evidence of a build/deploy job, not a substitute for a verified URL or a
product release. If the preview is unavailable, run the same build locally:

```sh
bun install --frozen-lockfile
cd frontend
VITE_DEPLOY_TARGET=pages bun run build
```

## macOS preview

The macOS workflow (`.github/workflows/macos-shell.yml`) runs on
`macos-latest`, installs MyGo, generates bindings, and uploads an unsigned
`darwin/arm64` app artifact. It is a CI artifact for evaluation, not a signed
or notarized distribution. There is no checked-in artifact URL; use the
workflow's artifact output after a successful run.

To build locally on an Apple Silicon Mac:

```sh
bun install
go install github.com/egoist/mygo/cmd/mygo@v0.1.22
mygo generate
bun run build -- -platform darwin/arm64
```

Review the resulting app before opening it. Signing, notarization, release
channels, and update delivery are deliberately out of scope.

## Branch relationship

- `migration/mygo-shell-poc` (this branch) is the UI-first shell experiment.
- `feature/go-backend-runtime` is the backend migration slice with Go HTTP/SSE,
  SQLite event storage, deterministic offline provider, Docker Compose, and
  backend-specific verification workflow.
- The existing DeepStudent implementation remains the source of truth until
  compatibility, performance, and security gates are agreed and met. Neither
  migration branch replaces it or changes its data schema by itself.

When integrating the branches, keep the runtime contract versioned and verify
both the frontend adapter and backend API against the same contract revision.

## Known limitations

- Demo chat is local `StubAdapter`; prompts are not sent to a model or backend.
- Model/runtime selections, attachments, tool, and deep-thinking controls are
  UI affordances only.
- Learning resources, tasks, skills, and flashcards are empty-state views with
  no persistence beyond the demo preferences.
- The health bridge reports process start time only; it does not prove backend
  readiness, provider connectivity, or durable storage.
- No authentication, authorization, remote-device discovery, offline sync,
  telemetry, cancellation, replay, or migration tooling is implemented.
- No Docker image or Compose service is defined on this branch.
- Go CI status is intentionally unverified here; rely on the backend branch's
  workflow for backend validation.

## Roadmap

1. Keep the shell contract-first and add a typed adapter interface separate
   from the local `StubAdapter`.
2. Connect a local development adapter to the backend branch's health and
   streaming endpoints, with explicit loading, timeout, and connection-lost UI.
3. Add contract and end-to-end tests that exercise the same runtime.v1 revision.
4. Persist real learning data only after schema, migration, and retention
   decisions are documented.
5. Add authentication, origin policy, cancellation/replay semantics, and
   provider secret handling before any shared or production deployment.
6. Establish accessibility, performance, signed/notarized macOS packaging,
   reproducible Pages artifacts, and release verification gates.
